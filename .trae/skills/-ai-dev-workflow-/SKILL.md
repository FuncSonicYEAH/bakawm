# AI 开发标准流程 Skill

> 定位：一套结构化、可回滚、可追溯的 AI 驱动开发流程。不是"想到哪做到哪"，而是每个阶段有明确的门禁条件和交付物，确保开发过程可控、结果可验证。

> **核心思想**：AI 开发最大的敌人不是技术难度，而是**需求漂移**和**质量衰减**。本流程通过三阶段门禁 + 双循环审查机制，在保证效率的同时守住质量底线。

## 阶段一：需求分析与澄清

### 目标
在动手写任何代码之前，确保对需求的理解与用户意图完全一致。

### 执行步骤

#### Step 1.1 — 初步分析

主 Agent 接收用户需求后，执行以下分析：

1. **理解需求**：用自己的话复述需求，确认理解无误
2. **标记不明确点**：列出所有模糊、歧义、缺失的信息，按影响程度分三级：
   - 🔴 阻塞级：不澄清无法继续
   - 🟡 风险级：不澄清可能导致返工
   - 🟢 细节级：不澄清影响体验但不影响核心功能
3. **输出初步分析报告**，格式如下：

```
📋 初步分析报告

【需求理解】
[用 3-5 句话复述你的理解]

【不明确点】
🔴 阻塞级（必须先澄清）：
  - [问题1]
  - [问题2]

🟡 风险级（建议澄清）：
  - [问题3]

🟢 细节级（可后续确认）：
  - [问题4]
```

#### Step 1.2 — 向用户澄清

1. 将 Step 1.1 的分析报告呈现给用户
2. **逐条询问**，不要一口气抛出所有问题
3. 每次用户回答后，**确认理解**再进入下一条
4. 澄清完毕后，输出**确认后的需求理解**，请用户签字

#### Step 1.3 — 拆分需求

1. 将确认后的需求拆分为独立的子任务
2. 每个子任务必须附带**原始需求原文引用**（用 `> 原文：` 标记）
3. 标注子任务之间的依赖关系
4. 对每个子任务评估是否需要 WebSearch 调研

输出格式：

```
📦 需求拆分

子任务 1：【名称】
  > 原文：[用户原话]
  依赖：无
  需要调研：是/否（原因）

子任务 2：【名称】
  > 原文：[用户原话]
  依赖：子任务 1
  需要调研：是/否（原因）
```

#### Step 1.4 — 并行 SubAgent 调研

1. 对需要调研的子任务，**并行启动**多个 SubAgent
2. 每个 SubAgent 的指令必须包含：
   - 原始需求原文
   - 项目上下文（当前技术栈、已有代码结构）
   - 调研方向（WebSearch 关键词建议）
   - 输出格式要求
3. 等待所有 SubAgent 返回结果后，进入 Step 1.5

#### Step 1.5 — 汇总分析

1. 合并所有 SubAgent 的调研结果
2. 标注冲突点（不同 SubAgent 返回矛盾结论时）
3. 生成**需求规格文档**，包含：
   - 需求概述
   - 功能需求清单
   - 非功能需求（性能、安全、兼容性等）
   - 技术约束
   - 风险与假设

### [门禁] 阶段一门禁

**必须满足以下条件才能进入阶段二：**

- [ ] 用户已确认需求规格文档
- [ ] 所有 🔴 阻塞级问题已解决
- [ ] 所有 🟡 风险级问题至少已有预案
- [ ] 需求规格文档已保存（作为后续验证的基准）

---

## 阶段二：方案设计与执行迭代

### 目标
将需求规格转化为可执行方案，通过开发→审查→修复的循环，确保交付质量。

### 执行步骤

#### Step 2.1 — 方案设计

基于阶段一的需求规格文档，输出：

1. **详细 ToDo List**：每个任务包含：
   - 任务编号（如 T-001）
   - 任务描述
   - 关联的需求原文
   - 预计涉及的文件
   - 完成标准（如何验证该任务已完成）
   - 优先级（P0/P1/P2）

2. **设计文档**（如涉及架构变更）：
   - 架构图（文字描述或 Mermaid）
   - 数据流
   - 接口定义
   - 关键决策记录

#### Step 2.2 — 项目规范化

1. 检查并规范化项目结构（目录命名、文件组织）
2. 撰写/更新相关 MD 文档：
   - 项目 README（如需要）
   - 开发规范文档
   - API 文档（如涉及）
3. 确保代码风格一致性（lint、formatter 配置）

#### Step 2.3 — 并行开发

1. 将 ToDo List 中**无依赖冲突**的任务分组
2. 每组并行启动 SubAgent 进行开发
3. 每个 SubAgent 的指令必须包含：
   - 具体任务描述 + 原文引用
   - 涉及的文件路径
   - 完成标准
   - 注意事项（与其它任务的冲突点）

#### Step 2.4 — 审查循环（核心质量保障）

这是整个流程的**质量核心**。不是一次审查就结束，而是循环直到通过。

**审查流程：**

```
┌──────────────────────────────────────┐
│          审查循环入口                  │
└──────────────┬───────────────────────┘
               ▼
┌──────────────────────────────────────┐
│  并行启动多个 SubAgent 审查            │
│  - 审查 Agent A：对照原始需求验证      │
│  - 审查 Agent B：代码质量 + 规范检查   │
│  - 审查 Agent C：边界情况 + 异常处理   │
└──────────────┬───────────────────────┘
               ▼
┌──────────────────────────────────────┐
│  汇总审查结果，生成问题清单             │
│  按优先级分级：                        │
│  🔴 阻塞：功能缺失/与需求不符/严重Bug  │
│  🟡 重要：代码质量/规范/性能问题       │
│  🟢 建议：优化建议/锦上添花            │
└──────────────┬───────────────────────┘
               ▼
         ┌────┴────┐
         │ 有问题？  │
         └────┬────┘
        ┌─────┴─────┐
        │           │
       有          无
        │           │
        ▼           ▼
   ┌─────────┐  ┌──────────┐
   │ 修复问题  │  │ 输出审查  │
   │ 回到入口  │  │ 通过报告  │
   └─────────┘  └──────────┘
```

**循环终止条件：**
- 无 🔴 阻塞级问题
- 🟡 重要级问题 ≤ 3 个且都有明确修复计划
- 最多循环 3 次（超过 3 次说明需求或方案本身有问题，需回到阶段一）

**审查报告格式：**

```
📊 审查报告（第 N 轮）

【审查维度】
- 需求符合度：X/10
- 代码质量：X/10
- 规范遵循：X/10
- 边界处理：X/10

【问题清单】
🔴 阻塞：N 个
  - [问题描述 + 涉及文件 + 建议修复方案]

🟡 重要：N 个
  - [问题描述 + 涉及文件 + 建议修复方案]

🟢 建议：N 个
  - [问题描述]

【结论】
✅ 通过 / ❌ 需要修复（第 N+1 轮）
```

### [门禁] 阶段二门禁

**必须满足以下条件才能进入阶段三：**

- [ ] 审查报告结论为"通过"
- [ ] 无 🔴 阻塞级问题
- [ ] 所有 🟡 重要级问题已修复或已有明确计划
- [ ] ToDo List 中所有 P0 任务已完成
- [ ] 代码可正常运行/构建

## 阶段三：验证与交付

### 目标
确保最终交付物与用户期望一致，给用户完整的知情权和决策权。

### 执行步骤

#### Step 3.1 — 完整性验证

1. 对照阶段一的需求规格文档，逐条验证
2. 生成验证清单：

```
✅ 完整性验证

【功能需求】
[需求1] ✅ 已实现 — [实现说明]
[需求2] ✅ 已实现 — [实现说明]
[需求3] ⚠️ 部分实现 — [说明 + 原因]

【非功能需求】
[性能] ✅ 满足 — [数据/说明]
[安全] ✅ 满足 — [措施说明]
```

#### Step 3.2 — 拆分输出

向用户呈现三个维度的总结：

**1. 过程总结（我们做了什么）**
- 从需求到交付的完整路径
- 每个阶段的决策和关键节点
- 遇到的难点和解决方案

**2. 实现内容（交付了什么）**
- 新增/修改的文件清单
- 核心功能说明
- 技术选型说明

**3. 关键决策（为什么这么做）**
- 重要的取舍和权衡
- 已知的限制和遗留问题
- 后续建议

#### Step 3.3 — 用户确认

1. 将 Step 3.2 的内容呈现给用户
2. 逐项询问确认
3. 给用户三种选择：
   - ✅ **确认通过**：结束对话，交付完成
   - 🔄 **需要修改**：回到阶段一，附带问题上下文
   - ❓ **还有疑问**：继续解答

### 流程结束条件

- 用户选择"确认通过"
- 选择"需要修改"时，回到阶段一，但**保留已有上下文**，避免重复分析

## 关键原则

### 1. 原文引用不可丢
从阶段一到阶段三，每个子任务、每个验证项都必须追溯到用户的原始需求原文。防止需求漂移。

### 2. 并行优先，但要有汇合
SubAgent 能并行的就并行，但每次并行后必须有汇总对比环节，不能直接跳过。

### 3. 门禁不可跳过
每个阶段的门禁条件是硬性的——不满足就不能进入下一阶段。如果用户催促，应解释风险而非直接跳过。

### 4. 审查循环不超过 3 轮
如果一个任务经过 3 轮审查修复仍有问题，说明不是执行问题，而是需求或方案本身有问题。此时应回到阶段一重新分析。

### 5. 状态透明
每个步骤完成后，必须告知用户当前阶段、进度、下一步计划。用户应该始终知道"现在在做什么"和"接下来要做什么"。

### 6. 文档即资产
所有中间产物（需求规格文档、设计文档、审查报告）都应保留，它们不仅是当前项目的依据，也是后续维护的参考。

### 7. 准确性优先，拒绝过度赞美
- **禁止过度夸赞**：不使用"太棒了""非常完美""绝妙的"等浮夸措辞。评价以事实为依据，好就说好在哪，有问题就说问题在哪。
- **双方判断均可质疑**：AI 的回答不一定正确，用户的判断也不一定正确。对待任何结论都应反复推敲，不盲从、不迎合。
- **主动索要证据**：当用户提出一个判断或结论时，如果 AI 认为可能存在偏差，应主动询问补充信息或证据，而非直接接受。
- **结构化输出**：所有回答保持结构化——先结论后分析、分点分层、条理清晰。避免长篇大论无重点。

## 执行检查清单（AI 自检用）

在流程执行过程中，AI 应定期自检：

- [ ] 每个子任务是否都有原文引用？
- [ ] 并行 SubAgent 后是否做了汇总对比？
- [ ] 阶段门禁是否真的满足（不是跳过）？
- [ ] 审查循环是否输出了正式报告？
- [ ] 用户是否在每个关键节点都做了确认？
- [ ] 最终交付前是否对照了需求规格文档？
- [ ] 回答中是否避免了过度夸赞，保持了结构化输出？
- [ ] 对用户提出的判断是否做了独立推敲，而非直接接受？
